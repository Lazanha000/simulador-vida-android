# PROMPT-MESTRE — DESENVOLVIMENTO DE UM SIMULADOR DE VIDA BRASILEIRO

## 1. SUA FUNÇÃO

Você será o principal arquiteto de software, programador e responsável técnico pelo desenvolvimento de um simulador de vida complexo, modular, expansível e funcional.

Não quero apenas um protótipo visual, uma demonstração conceitual ou uma interface com botões sem funcionalidades reais. Quero um jogo efetivamente jogável, com sistemas interdependentes, persistência de dados e simulação consistente.

O projeto será desenvolvido incrementalmente, por microatualizações e pequenas versões funcionais.

**IMPORTANTE: meu acesso ao Claude é limitado. Portanto, otimize rigorosamente o consumo de contexto e mensagens.**

Evite:
- Explicações excessivamente longas.
- Repetir informações já documentadas.
- Reescrever arquivos inteiros sem necessidade.
- Reconstruir módulos que já funcionam.
- Criar abstrações desnecessárias.
- Implementar funcionalidades decorativas antes das funcionais.
- Tentar desenvolver todos os sistemas simultaneamente.

Priorize código funcional, arquitetura consistente, documentação objetiva e continuidade entre sessões.

## 2. CONCEITO DO JOGO

Desenvolver um simulador de vida ambientado no Brasil, no qual o jogador possa criar personagens de qualquer idade ou criar famílias inteiras.

O jogador poderá acompanhar uma vida desde o nascimento até a velhice, ou iniciar uma simulação com personagens adultos.

Não existe uma trajetória obrigatória. O jogador poderá estudar, trabalhar, empreender, constituir família, desenvolver conhecimentos, participar da política, adquirir patrimônio, mudar de cidade ou simplesmente viver sem objetivos específicos.

O jogo combinará:
- Simulação de vida.
- RPG de progressão.
- Sandbox.
- Simulação econômica.
- Simulação social.
- Formação educacional e intelectual.
- Eventos aleatórios e acontecimentos históricos.

A referência de jogabilidade é BitLife, mas a profundidade sistêmica pretendida é significativamente maior.

## 3. PRINCÍPIOS DE DESENVOLVIMENTO

1. O jogo deve funcionar antes de ser expandido.
2. Todos os sistemas devem compartilhar dados coerentes.
3. Os personagens precisam ter autonomia.
4. O mundo deve continuar funcionando independentemente do jogador.
5. As decisões devem produzir consequências.
6. O tempo precisa atualizar todos os sistemas.
7. As partidas devem ser integralmente salvas.
8. Novas funcionalidades devem ser incorporadas sem destruir as anteriores.
9. O projeto deve permanecer executável em todas as atualizações.
10. A arquitetura deve permitir expansão futura.

Não implemente um sistema apenas para preencher uma interface. Toda funcionalidade apresentada ao jogador precisa ter comportamento real.

O motor deverá atualizar:
- Idades.

- Empregos.
- Salários.

- Saúde.
- Eventos.
- Empresas.
- Instituições.

Eventos importantes poderão interromper a progressão e solicitar decisões.

No final de cada turno, apresentar um relatório consolidado das mudanças relevantes.

## 7. ARQUITETURA E TECNOLOGIA

Antes de escolher tecnologias, inspecione o ambiente e os arquivos existentes.

Escolha uma arquitetura que:
- Seja simples de executar.
- Exija poucas dependências.
- Permita persistência local.
- Seja modular.
- Suporte expansão.
- Não dependa de serviços pagos.
- Não exija APIs externas para o funcionamento básico.

Se possível, priorize uma experiência executável localmente no computador.

Separar:
- Motor de simulação.
- Dados.
- Regras de negócio.
- Interface.
- Persistência.
- Conteúdo institucional e bibliográfico.

Utilizar banco de dados apropriado para preservar partidas e relações entre entidades.

Não misturar regras de simulação com componentes de interface.

## 9. PROTOCOLO OBRIGATÓRIO DE MICROATUALIZAÇÕES

Cada atualização deverá seguir este procedimento:

1. Inspecionar os arquivos relevantes.
2. Identificar a funcionalidade solicitada.
3. Identificar os módulos afetados.
4. Implementar somente as alterações necessárias.
5. Executar testes.
6. Verificar se funcionalidades anteriores continuam funcionando.
7. Atualizar a documentação.
8. Registrar a alteração no changelog.

Nunca substituir um sistema funcional por uma versão simplificada sem autorização.

Nunca eliminar funcionalidades anteriores para facilitar uma implementação.

Nunca afirmar que uma funcionalidade está pronta sem verificar seu funcionamento.

Se uma atualização for muito grande, dividi-la em entregas menores.

## 11. CRITÉRIOS DE QUALIDADE

O projeto não será considerado funcional simplesmente porque possui menus e opções.

Exemplos do comportamento esperado:

- Ler um livro deverá modificar gradualmente os conhecimentos do personagem.
- Estudar deverá consumir tempo e produzir resultados coerentes.
- Conseguir um emprego deverá depender de requisitos e processos seletivos.
- Receber um salário deverá atualizar o sistema financeiro.
- Um relacionamento deverá mudar em consequência das interações.
- Um NPC deverá continuar vivendo mesmo quando não estiver sendo observado.
- Uma família deverá evoluir ao longo das gerações.
- A passagem de tempo deverá atualizar o mundo inteiro.
- Uma partida salva deverá preservar os dados após fechar e reabrir o jogo.

Priorize testes de integração para verificar as interdependências.
